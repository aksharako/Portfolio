01 / the brief

Texas homeowners overpay every year.

Every spring, Texas homeowners get a notice from their county appraisal district telling them what their home is "worth" — and, therefore, what they owe in property tax. Assessments are often inflated. The protest process exists, but almost no one uses it: it's confusing, the deadlines are strict, and building a case with comparable properties takes hours of research.

Property Tax Pro closes that gap. A homeowner enters their address; a multi-agent AI pipeline pulls their property record, finds comps in their neighborhood, computes what their home is actually worth, and generates a ready-to-file protest package — letter, talking points, and comp exhibit — in under a minute.

I designed the whole consumer experience and built the frontend that visualizes it.

02 / the pipeline

Six agents, one verdict.

The heart of the app is a six-agent pipeline. Each agent has a spec, a role, and a confidence score. Results stream to the browser in real time via EventSource, so the user watches the analysis unfold instead of staring at a spinner.

04 / a product decision

We took a feature out.

An early version had a fourth screen: "Hold to file." The user could sign and submit their protest to the county appraisal district right from the app. It felt magical. It also opened up serious problems.

Filing a property tax protest involves county-specific forms, hard legal deadlines, and rules that vary by jurisdiction. If the app filed on someone's behalf and got it wrong, we were on the hook. So we removed it.

The new positioning

We arm you with the evidence. You file the protest.

The verdict screen ends with a PDF download of the complete protest package — letter, talking points, comp exhibit. Users take it to their county appraisal district and file offline. No liability, no time pressure inside the app, and the user stays in control of their own legal filing.

This was the single hardest product call — cutting the most visually satisfying feature. It made the app narrower, more honest, and more useful.

05 / the build

Two front-ends, one pipeline.

The frontend is React 18 + TypeScript + Vite. It ships two very different interfaces on top of the same pipeline:

i.

Consumer flow

Three screens. Warm, hand-holdy. Meets homeowners where they are.

ii.

Ops console

Full agent traces, confidence scores, tool calls. For the team.

iii.

Shared streaming

One usePipelineStream hook. EventSource. Same data, two views.

React 18 TypeScript Vite CSS Modules EventSource (SSE) jsPDF Vitest Testing Library TDD

Tests are Vitest with coverage. State transitions are TDD'd. The consumer flow is a small, explicit state machine (land → processing → verdict → error) — easy to reason about, easy to test.

06 / what I learned

Designing for AI is designing for uncertainty.

A pipeline of six agents doesn't always agree with itself. Validation might flag issues. Retrieval might not find enough comps. Reasoning might give a low-confidence verdict. Traditional UX assumes the answer exists — AI UX has to teach the user how to trust an answer that came with a probability attached.

The processing screen with the streaming agent trace was the answer. Showing the work — acquisition done, validation done, retrieval done, reasoning running… — turns "wait 45 seconds staring at a spinner" into "watch six specialists analyze your home." Same latency, completely different feeling.
